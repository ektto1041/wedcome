# 하객 인생샷 이미지·영상 업로드 및 Hero Story 연동 검토

## 1. 검토 결론

기능 구현은 가능하다. 현재 Hero는 이미지와 영상을 함께 재생하고 앞·현재·뒤 Story만 렌더링하므로, 하객이 올린 이미지·영상 Story를 합치는 기반도 이미 갖춰져 있다.

다만 기획을 그대로 구현하기보다 아래와 같이 조정하는 것을 권장한다.

1. UID당 이미지 또는 영상 중 하나만 업로드할 수 있게 한다.
2. 이미지는 원본 용량과 관계없이 선택하고 모바일 브라우저에서 리사이즈·재인코딩한다.
3. 영상은 클라이언트에서 압축하지 않고 `MP4`, 최대 `10초`, 최대 `20MB`로 제한해 직접 업로드한다.
4. 미디어 파일은 Cloud Storage, 목록·상태·정렬 정보는 Firestore에 저장한다.
5. Hero는 Storage의 파일을 직접 `listAll()`하지 않고 Firestore 문서를 구독한다.
6. 업로드 완료 후 새로고침하지 않는다. Firestore `onSnapshot()` 또는 로컬 상태 반영으로 즉시 Story 목록에 추가한다.
7. 업로드 미디어가 하나라도 있으면 기본 Hero 목록을 하객 미디어 전용으로 전환한다.
8. 사용자가 `우리 이야기 보기`를 누르면 기존 정적 Hero로 전환하고, `하객 인생샷 보기`로 다시 돌아올 수 있게 한다.
9. 전체 하객은 약 200명이지만 실제 업로더는 50명 이하, UID당 미디어 1개로 가정한다. 이 범위에서는 업로드 미디어 전체를 하나의 Hero Story로 구성할 수 있다.
10. 보안은 신뢰 기반으로 가볍게 구성한다. 익명 인증, UID별 고정 경로, MIME·용량 검사만 최소 안전장치로 둔다.

Cloud Storage는 2026년 2월 3일부터 Blaze 요금제 연결이 필수다. 무상 사용량은 남아 있지만 결제수단 없이 Spark 요금제만으로 사진 저장 기능을 운영할 수는 없다.

## 2. 현재 프로젝트 기준 확인 결과

### 이미 준비된 부분

- `firebase` SDK가 설치되어 있다.
- Firebase 앱 설정에 `storageBucket` 환경 변수가 이미 포함되어 있다.
- Firestore 초기화 코드와 RSVP용 보안 규칙이 존재한다.
- Hero는 로컬 이미지와 영상을 동일한 Story 목록으로 다룬다.
- 이미지 Story의 표시 시간은 이미 `3,000ms`로 설정되어 있다.
- 현재 Story와 인접 Story만 DOM에 렌더링하므로 이미지 개수가 늘어도 모든 원본을 동시에 다운로드하지는 않는다.
- 이미지 로드 실패 시 해당 Story를 제외하는 처리도 존재한다.

### 추가가 필요한 부분

- Firebase Authentication 초기화 및 익명 로그인
- Firebase Storage 초기화
- `storage.rules`와 `firebase.json`의 Storage 배포 설정
- 업로드 가능 시각 판정
- 안내 Bottom Sheet 또는 Dialog
- 이미지 디코딩, 리사이즈, 재인코딩 유틸리티
- 영상 길이·용량·재생 가능 여부 검사
- 업로드 진행률·재시도 UI
- UID별 미디어 문서와 Story 메타데이터용 Firestore 구조 및 최소 규칙
- 원격 Story 구독 훅과 정적 Story 병합 로직
- 하객 Story와 기존 Story 전환 UI

기존 `BottomSheet` 컴포넌트는 업로드 안내 UI에 재사용 가능성을 먼저 검토할 수 있다. 새로운 UI 라이브러리를 추가할 필요는 없다.

## 3. 권장 사용자 흐름

```text
예식 당일 00:00 KST 이전
  └─ 업로드 버튼을 렌더링하지 않음

예식 당일 00:00 KST 이후
  └─ 진행 바 아래에 “인생샷 추가하기” 버튼 표시
       └─ 안내 팝업
            ├─ 세로 이미지·영상 권장
            ├─ 이미지 또는 MP4 영상 1개
            ├─ 영상은 10초·20MB 이하
            └─ 이미지는 업로드 전에 자동 최적화됨
                 └─ 미디어 선택(1개)
                      ├─ 이미지: 클라이언트 압축
                      └─ 영상: 길이·용량 검사
                           └─ 파일 업로드
                                └─ Firestore Story 등록
                                     └─ 성공 안내
                                          └─ 새로고침 없이 Hero에 반영
```

파일 선택창에서는 `accept="image/*,video/mp4"`를 사용한다. `accept`는 선택 UI를 돕는 힌트일 뿐 검증 수단이 아니므로, 이미지 디코딩 여부와 영상의 MIME·길이·용량을 별도로 확인해야 한다.

## 4. 예식 당일 노출 조건

현재 청첩장의 예식일은 `2026-10-03 16:30 KST`이다. “예식 당일부터”는 우선 `2026-10-03 00:00:00 KST`, 즉 `2026-10-02T15:00:00Z`부터로 해석한다.

권장 정책은 다음 두 층으로 나눈다.

- UI 노출: KST 기준 시각으로 버튼을 표시한다.
- 실제 쓰기 허용: Firestore 및 Storage Security Rules에서 서버의 `request.time`으로 시작 시각을 검사한다.

클라이언트 시계만 사용하면 사용자가 기기 날짜를 바꿔 사전 업로드할 수 있다. UI 판정은 편의를 위한 것이고 서버 규칙이 최종 권한이어야 한다.

종료 시각은 현재 기획에 없다. 그대로라면 예식일 이후 계속 버튼이 노출된다. 운영 전에 아래 중 하나를 결정해야 한다.

- 종료 없음
- 예식 다음 날 자정 종료
- 운영자가 Firestore 설정 문서의 `uploadEnabled` 값을 끄면 종료

운영 대응을 고려하면 세 번째 방식을 권장한다. 단, 설정 문서를 읽지 못했을 때는 기본적으로 업로드를 닫는 fail-closed 동작이 필요하다.

## 5. 이미지 선택과 클라이언트 압축

### “파일 크기 제한 없음”의 정확한 의미

파일 선택 단계에서 `5MB 이하만 선택 가능` 같은 제한을 두지 않는다. 10~30MB의 휴대폰 원본도 선택할 수 있게 하고, 원본은 네트워크로 보내기 전에 브라우저에서 최적화한다.

그러나 웹 브라우저에서 문자 그대로 무제한 파일을 보장할 수는 없다. 압축 전에는 전체 픽셀을 메모리에 디코딩해야 하므로 초고해상도 이미지나 손상된 파일은 모바일 Safari가 탭을 종료시킬 수 있다. 사용자에게는 용량 제한을 노출하지 않더라도 다음 방어 처리가 필요하다.

- 한 번에 1장만 선택
- 디코딩 실패 시 원본 업로드 금지 및 친절한 오류 표시
- 비정상적으로 큰 픽셀 수는 처리 중단
- 압축 중 버튼 중복 실행 방지
- 탭이 백그라운드로 전환되어도 중복 업로드되지 않도록 상태 관리

### 초기 압축 정책

| 항목 | 권장 초기값 |
| --- | --- |
| 입력 | 브라우저가 디코딩 가능한 이미지 |
| 출력 | `image/webp`, 실패 시 `image/jpeg` |
| 긴 변 | 최대 `1920px` |
| 최초 품질 | `0.82` |
| 목표 크기 | 약 `1.5MB` 이하 |
| 업로드 허용 상한 | `5MB` |
| 처리 방식 | 이미지 한 장씩 순차 처리 |

목표 크기를 넘으면 품질을 단계적으로 낮추고, 그래도 넘으면 해상도를 한 단계 더 축소한다. 최종 결과가 `5MB`를 넘는 경우에는 Storage Rules에서 거부한다. 이 상한은 원본 선택 제한이 아니라 서버 비용·오남용을 막는 압축 결과물 제한이다.

Canvas로 다시 인코딩하면 일반적으로 EXIF/GPS 메타데이터가 제거되어 개인정보 측면에서도 유리하다. 다만 다음 항목은 실제 iPhone Safari와 Android Chrome에서 확인해야 한다.

- HEIC/HEIF 디코딩 가능 여부 및 실패 안내
- EXIF 회전이 올바르게 적용되는지
- 투명 PNG가 JPEG fallback에서 검은 배경으로 변하지 않는지
- 저메모리 기기에서 고해상도 사진 1장 처리 안정성
- WebP 인코딩 실패 시 JPEG fallback

초기 구현은 브라우저 API(`createImageBitmap`, Canvas, `toBlob`)로 충분하다. 실기기 검증에서 HEIC나 회전 문제를 해결하지 못할 때만 전용 라이브러리 도입을 검토한다.

## 6. 영상 업로드

영상 압축과 트랜스코딩은 고려하지 않는다. 사용자가 선택한 원본 파일을 그대로 Cloud Storage에 업로드한다.

### 권장 제한

| 항목 | 권장 초기값 |
| --- | --- |
| 파일 형식 | MP4 (`video/mp4`) |
| 최대 재생 시간 | 10초 |
| 최대 파일 크기 | 20MB |
| 업로드 방식 | `uploadBytesResumable` 직접 업로드 |
| Hero 재생 | 음소거, 원본 영상 길이만큼 재생 |
| 화면 맞춤 | `object-fit: cover` |

10초는 Story 흐름을 지나치게 늘리지 않으면서 짧은 예식 장면을 담을 수 있는 길이다. 20MB는 모바일 네트워크에서 직접 업로드할 수 있는 현실적인 상한과 Storage 전송량 사이의 절충값이다. 실제 사용 후 실패율이 높으면 30MB까지 완화할 수 있지만, 첫 배포부터 크게 잡는 것은 권장하지 않는다.

파일을 선택하면 임시 object URL로 `<video preload="metadata">`를 만들고 `loadedmetadata` 이후 `duration`을 확인한다. 10초 또는 20MB를 넘으면 업로드를 시작하지 않고 다른 영상을 선택하도록 안내한다. Storage Rules에서는 MIME과 20MB 상한을 다시 검사할 수 있지만 영상 길이는 검사할 수 없으므로, 길이 제한은 신뢰 기반의 클라이언트 검사로 둔다.

### 형식과 호환성

MP4는 컨테이너 이름일 뿐 내부 코덱까지 보장하지 않는다. H.264 영상은 주요 모바일 브라우저에서 가장 호환성이 높지만, HEVC 등으로 촬영된 MP4는 일부 기기에서 재생되지 않을 수 있다. 영상 변환을 하지 않는 조건에서는 모든 휴대폰 영상의 교차 기기 재생을 완전히 보장할 수 없다.

가벼운 구현에서는 다음 수준으로 처리한다.

- 파일 선택은 `video/mp4`만 허용한다.
- 선택한 기기에서 `<video>` metadata를 읽지 못하면 업로드를 거부한다.
- 재생 기기에서 오류가 발생하면 현재 Hero의 실패 Story 제외 로직으로 해당 영상을 건너뛴다.
- 업로드 안내에 `10초 이하 MP4 영상만 가능하며 소리는 재생되지 않습니다`라고 명시한다.
- MOV, WebM 및 브라우저가 재생하지 못하는 영상은 첫 버전에서 지원하지 않는다.

영상 압축, 자르기, 코덱 변환과 서버 트랜스코딩은 모두 이번 구현 범위에서 제외한다.

## 7. 저장 구조

### Cloud Storage

```text
weddings/2026-10-03/guest-stories/{uploaderId}/media
```

확장자와 관계없이 파일 경로를 UID별 `media` 하나로 고정한다. 이미지와 영상 중 무엇을 선택해도 UID가 소유하는 Storage 객체는 하나뿐이다. 같은 경로 덮어쓰기를 허용하면 사진·영상 교체 기능도 간단하게 제공할 수 있다.

### Firestore

```text
weddings/{weddingId}
  uploadEnabled: boolean
  uploadStartsAt: Timestamp

weddings/{weddingId}/guestStories/{uploaderId}
  uploaderId: string
  storagePath: string
  mediaType: "image" | "video"
  contentType: "image/webp" | "image/jpeg" | "video/mp4"
  byteSize: number
  width: number
  height: number
  durationMs: number | null
  status: "uploading" | "ready"
  createdAt: server timestamp
```

다운로드 URL보다는 `storagePath`를 원본 값으로 저장하는 편이 낫다. 파일 이동·삭제와 데이터 정합성을 확인하기 쉽고, 임의 외부 URL을 Story에 주입하는 것도 막을 수 있다.

상태는 `uploading`과 `ready`만 둔다. 특정 미디어를 내려야 하면 첫 버전에서는 Firebase Console에서 문서와 파일을 직접 삭제한다.

## 8. UID당 미디어 1개 제한

### MVP: 익명 인증 UID당 미디어 1개

페이지 진입 시 Firebase Anonymous Authentication으로 UID를 발급하고, 해당 UID 아래에 이미지 또는 영상 하나만 저장한다.

장점:

- 별도 로그인 화면이 없다.
- 이미지와 영상에 같은 제한 방식을 사용할 수 있다.
- 현재 앱의 간단한 사용자 흐름에 적합하다.

한계:

- 브라우저 저장소를 삭제하거나 시크릿 모드·다른 기기를 사용하면 새 UID가 발급된다.
- 따라서 이것은 엄밀한 “사람당 1개”가 아니라 “익명 계정당 1개”다.

### 업로드 문서 처리

신뢰 기반 MVP에서는 별도 서버 트랜잭션이나 예약 시스템을 두지 않는다.

1. UID와 같은 ID의 Firestore 문서가 있는지 확인한다.
2. 없으면 이미지 압축 또는 영상 검사를 수행한다.
3. UID에 대응하는 고정 Storage 경로에 파일을 업로드한다.
4. 업로드 성공 후 같은 UID의 문서를 `ready`로 저장한다.
5. 실패하면 같은 경로로 재시도한다.

Storage와 Firestore는 하나의 트랜잭션으로 묶이지 않지만, UID별 경로와 문서가 각각 하나뿐이므로 같은 경로 재시도로 단순하게 복구할 수 있다.

## 9. 최소 보안 규칙

사용자를 신뢰하는 운영을 전제로 복잡한 초대 코드, 관리자 승인, 서버 검증은 도입하지 않는다. 다만 공개 쓰기를 완전히 허용하면 자동화된 외부 요청이 Storage 비용을 만들 수 있으므로 익명 인증과 파일 상한은 유지한다.

Storage 쓰기 조건의 개념은 다음과 같다.

- 인증된 사용자만 허용
- 경로의 `{uploaderId}`가 `request.auth.uid`와 같음
- UID별 파일명은 `media` 하나만 허용
- 예식 당일 서버 시각 이후이며 업로드 기능이 활성 상태
- 이미지는 WebP/JPEG 및 5MB 이하
- 영상은 MP4 및 20MB 이하

Firestore 문서 생성·수정 조건의 개념은 다음과 같다.

- 문서 ID가 `request.auth.uid`와 정확히 같음
- `storagePath`가 허용된 자신의 고정 경로와 정확히 일치
- `createdAt == request.time`
- 목록 읽기는 허용

App Check, 콘텐츠 검수, 관리자 승인 화면은 첫 구현 범위에서 제외한다. 필요가 생기면 이후 추가한다.

## 10. Hero 데이터 조회와 새로고침 여부

### Storage 직접 목록 조회를 권장하지 않는 이유

Cloud Storage `listAll()`은 작은 디렉터리용이며 결과 전체를 메모리에 버퍼링한다. 목록을 읽는 동안 파일이 추가·삭제되면 일관된 스냅샷도 보장하지 않는다. 또한 정렬, 공개 상태, 숨김 처리와 실시간 갱신을 표현하기 어렵다.

따라서 다음처럼 역할을 분리한다.

- Storage: 실제 압축 이미지 또는 원본 MP4 바이트
- Firestore: Story 목록, 순서, 상태, 생성 시각, Storage 경로

### 새로고침은 필요 없음

Hero에서 `status == "ready"`인 문서를 `onSnapshot()`으로 구독하면 업로드 완료 문서가 생성되는 즉시 목록에 반영된다. 같은 브라우저에서는 업로드 성공 결과를 로컬 상태에 먼저 추가하고 listener 결과와 ID로 중복 제거하면 체감 반응이 더 빠르다.

원격 목록을 다시 정렬하면서 현재 `activeIndex`가 다른 미디어를 가리키지 않도록 주의해야 한다. 재생 중인 Story ID를 기준으로 현재 항목을 유지하고, 새 미디어는 현재 세션 큐의 뒤에 추가하는 방식을 권장한다.

## 11. 하객 Story와 기존 Hero 전환

업로드된 `ready` 미디어가 하나라도 있으면 기본 재생 목록을 하객 Story로 전환한다. 이 문서에서 `업로드 미디어`는 이미지와 영상을 모두 뜻한다.

```text
업로드 미디어 0개
  └─ 기존 정적 Hero만 표시

업로드 미디어 1개 이상
  └─ 하객 Story만 표시
       ├─ “우리 이야기 보기” → 기존 정적 Hero
       └─ “하객 인생샷 보기” → 하객 Story
```

권장 상태는 `storySource: "guest" | "original"` 하나다.

- 초기 조회 결과가 1개 이상이면 `guest`, 0개면 `original`로 설정한다.
- `guest`와 `original` 재생 목록을 합치지 않는다.
- 전환 시 진행 바와 활성 인덱스를 해당 목록의 첫 항목으로 초기화한다.
- 하객 Story가 모두 삭제되거나 로드에 실패하면 자동으로 `original`로 fallback한다.
- 사용자가 기존 Hero를 직접 선택한 상태에서는 새 업로드가 도착해도 강제로 하객 Story로 전환하지 않는다.
- 선택 상태는 우선 현재 페이지 세션에서만 유지한다. 재방문하면 다시 하객 Story를 기본으로 보여준다.

전환 버튼은 진행 바 아래 업로드 버튼과 함께 배치하되 Hero 탭 영역보다 높은 `z-index`를 사용한다. 문구는 현재 상태의 반대 행동을 나타내야 한다.

- 하객 Story 재생 중: `우리 이야기 보기`
- 기존 Hero 재생 중: `하객 인생샷 보기`

## 12. 모든 업로드 미디어를 하나의 Story로 제공

전체 하객 약 200명 중 실제 업로더는 50명 이하이고, UID당 미디어 1개를 전제로 한다. 따라서 하객 Story는 최대 약 50개다.

- 50개가 모두 이미지면 한 바퀴는 약 2분 30초다.
- 50개가 모두 10초 영상이면 한 바퀴는 최대 약 8분 20초다.
- 이미지 25개와 10초 영상 25개라면 약 5분 25초다.
- 방문자 200명이 원격 문서 50개를 최초 조회하면 약 10,000 Firestore reads다.
- 200명이 접속한 상태에서 미디어 50개가 차례로 추가되면 실시간 갱신으로 최대 약 10,000 reads가 더 발생할 수 있다.
- 50개 진행 바 구간은 모바일에서 좁아지므로 표시 방식 보완이 필요하다.

### 권장안

- `ready` 상태인 업로드 미디어 전체를 하객 Story에 포함한다.
- 현재·이전·다음 미디어만 렌더링하는 기존 전략을 유지한다.
- 최초 목록은 Firestore에서 최대 50~60개 범위로 한 번 조회하고 이후 변경을 실시간 구독한다.
- 재생 중인 Story ID를 유지하고 새 미디어는 현재 세션 큐 뒤에 추가한다.
- Story가 많아지면 전체 구간을 모두 그리는 대신 현재 위치 주변 구간만 표시하거나 `현재 / 전체` 보조 표기를 사용한다.
- 예상치를 벗어난 업로드를 방어하도록 쿼리 안전 상한은 `100` 정도로 둔다.

### 전제 초과 시 대응

- 실제 업로더가 50명을 크게 넘으면 Hero 쿼리 상한, 진행 바, 전체 재생 시간이 다시 문제가 된다.
- 이 경우에만 Hero 노출 수 제한 또는 별도 전체 갤러리 분리를 적용한다.
- Firebase 사용량과 예산 알림은 예상 범위와 무관하게 설정한다.

현재 전제에서는 모든 업로드 미디어를 하나의 하객 Story로 제공할 수 있다. 다만 영상 비중이 높으면 전체 재생 시간이 길어지는 점은 허용해야 한다.

## 13. 업로드 UI 상태

버튼은 진행 바 바로 아래에 두되 기존 `StoryPicker` 및 재생 버튼과 겹치지 않게 배치해야 한다. 전체 Hero 탭 영역보다 높은 `z-index`를 주고, 최소 44×44px 터치 영역을 확보한다.

강조 효과는 계속 움직이는 강한 애니메이션보다 다음 정도가 적절하다.

- 사진·영상 아이콘과 명확한 라벨
- 반투명 밝은 배경 및 대비되는 글자색
- 최초 노출 시 1~2회만 약한 pulse
- `prefers-reduced-motion`에서는 pulse 제거
- 업로드 완료 후 버튼을 완료 상태로 변경: `인생샷을 추가했어요`

필요한 상태는 다음과 같다.

```text
idle
→ 안내 팝업
→ selecting
→ 이미지: compressing / 영상: validating
→ uploading(진행률)
→ saving
→ success

각 단계에서 실패하면 retry 또는 cancel
```

검사·압축·업로드 중에는 Hero 자동 재생을 일시정지한다. 완료 또는 취소 후 기존 재생 상태로 복귀한다.

## 14. 신뢰 기반 즉시 공개

업로드가 끝나면 별도 승인 없이 즉시 `ready`로 등록한다. 콘텐츠 검수, 신고, 관리자 승인 화면은 구현하지 않는다.

- 문제 발생 시 Firebase Console에서 해당 Firestore 문서와 Storage 객체를 직접 삭제한다.
- 전체 업로드는 `uploadEnabled` 값으로 끌 수 있게 한다.
- 사용자에게 업로드 즉시 공개된다는 점을 안내한다.

별도 운영 UI는 실제 필요가 생긴 뒤 추가한다.

## 15. 비용 및 Firebase 요금제

Firestore 무료 할당량은 저장 1GiB, 일 50,000 reads, 20,000 writes, 20,000 deletes다. 최대 50개 업로드 문서와 약 200명의 하객이라는 전제에서는 메타데이터 용량과 쓰기 횟수에 여유가 있다. 최초 목록 읽기와 실시간 변경 읽기를 합친 예상치도 무료 범위 안이지만 반복 접속 횟수에 따라 증가할 수 있다.

Cloud Storage는 Blaze 요금제 연결이 필요하다. 신규 기본 버킷 기준 무상 사용량에는 저장 5GB-months, 다운로드 100GB/month, 업로드 작업 5,000회/month, 다운로드 작업 50,000회/month가 포함된다. 지역과 버킷 유형에 따라 조건이 달라질 수 있으므로 실제 프로젝트 콘솔의 버킷 위치와 요금표를 배포 전에 확인해야 한다.

이미지만 50장이고 평균 1MB라면 저장량은 약 50MB다. 영상이 모두 허용 상한인 20MB라면 최대 약 1GB다. 이미지 25장과 영상 25장이 각각 1MB, 20MB라면 약 525MB다.

200명이 혼합 예시의 모든 미디어를 끝까지 내려받으면 단순 계산상 약 105GB가 되어 신규 기본 버킷의 월 무상 다운로드 100GB에 근접하거나 넘을 수 있다. 실제로는 모든 하객이 5분 이상 전체 Story를 보지 않을 가능성이 높고 브라우저 캐시도 작동하지만, 영상 원본을 압축하지 않는 만큼 다운로드 트래픽이 가장 큰 비용 변수다.

반드시 다음을 설정한다.

- Google Cloud Billing 예산 알림
- Firebase 사용량 모니터링
- 업로드 시작·종료 스위치
- 이미지 5MB·영상 20MB의 Storage Rules 상한
- Hero 쿼리 `limit`

## 16. 권장 구현 단위

### 1단계: 기반과 규칙

- Auth 및 Storage 초기화
- 익명 인증 활성화
- Firestore 데이터 모델 확정
- 간단한 Firestore·Storage Rules 작성 및 검증

### 2단계: 업로드 UX

- 당일 노출 조건
- 강조 버튼과 안내 Bottom Sheet
- 이미지·MP4 파일 선택 및 형식 검증
- 이미지 압축
- 영상 10초·20MB 검사
- 업로드 진행률, 오류·재시도
- UID별 고정 경로 Storage 업로드와 Firestore 문서 저장

### 3단계: Hero 연동

- `useGuestStories` 구독 훅
- 하객 Story와 기존 Story 목록 분리
- `storySource` 전환 UI
- 업로드 완료 즉시 큐 뒤에 추가
- 현재 Story ID 유지
- 원격 미디어 실패 시 건너뛰기와 기존 Hero fallback

### 4단계: 실기기 검증

- iPhone Safari/Android Chrome 테스트
- MP4 교차 기기 재생 테스트
- 느린 네트워크, 재시도와 업로드 중 화면 잠금 테스트
- 할당량·비용 알림 확인

## 17. 구현 전 결정이 필요한 항목

1. `예식 당일`의 시작을 00:00 KST로 볼지, 예식 시작 시각으로 볼지
2. 업로드 종료 시각 또는 수동 종료 기능을 둘지
3. MP4 영상 제한을 10초·20MB로 확정할지
4. 업로더가 자신의 미디어를 교체할 수 있는지
5. Story가 많을 때 진행 바를 주변 구간형과 `현재 / 전체` 중 어느 방식으로 표시할지

## 18. 권장 최종 사양

현재 프로젝트에는 아래 사양이 가장 균형이 좋다.

- `2026-10-03 00:00 KST`부터 버튼 노출
- 운영자가 `uploadEnabled`로 종료 가능
- 익명 인증 UID당 이미지 또는 영상 1개
- 이미지는 원본 선택 용량 제한 없이 클라이언트 자동 압축
- 이미지 긴 변 1920px, 목표 1.5MB, 압축본 상한 5MB
- 영상은 MP4 원본 직접 업로드, 최대 10초·20MB, 압축·변환 없음
- Storage에 미디어, Firestore에 Story 메타데이터
- Firestore 실시간 구독으로 새로고침 없이 반영
- 별도 승인 없이 즉시 공개
- 업로더 50명 이하를 전제로 전체 업로드 미디어를 하객 Story에 포함
- 업로드 미디어가 있으면 하객 Story만 기본 표시
- `우리 이야기 보기`와 `하객 인생샷 보기`로 두 목록 전환
- 예상치 초과를 방어하기 위해 Firestore 쿼리 안전 상한 100 적용
- Story 개수가 많을 때 진행 바와 현재 위치 표기 방식 조정

이 사양은 사용자를 신뢰하는 가벼운 운영을 전제로 하며, UID 제한을 우회하거나 호환되지 않는 MP4를 올리는 예외까지 완벽하게 방어하지 않는다.
